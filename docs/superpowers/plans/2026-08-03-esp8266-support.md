# ESP8266 Support Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Add the ESP8266 to the catalog as one module (`esp8266`, an ESP-12F) and two dev boards (`nodemcu-v1`, `d1-mini`), with the same pin warnings, flashing, ESPHome, specs, and SEO coverage every ESP32 page already has.

**Architecture:** The ESP8266 becomes a new `Family` in `src/data/chips/catalog.ts`. Its pin names, schematic symbol, and pad layout are generated by `scripts/generate-chip-data.mjs`, extended to read KiCad's own stock libraries in addition to Espressif's (Espressif's KiCad library has no ESP8266 parts). The two boards are `contrib/boards/*.board.json` files resolved against that module, which is the existing no-KiCad contribution path.

**Tech Stack:** Vite + React 19 + TypeScript + Tailwind 3 + Vitest. Generator is plain Node ESM. No new runtime dependencies.

## Global Constraints

- **No en dashes or em dashes anywhere in UI text, data files, or generated output.** Plain hyphens only. This is a hard project rule and the generator templates already comply.
- **Never hand-edit `src/data/chips/generated.ts`.** It is regenerated by the script. All manual additions go in `enrich.ts` (additive names and capabilities only) or `catalog.ts`.
- **Pin facts come from primary sources only.** The datasheet, the vendor's own schematic, or the upstream `arduino-esp8266` variant header. Never from a third-party pinout image. A previous board shipped upside down because a third-party image was trusted.
- **Product name stays "ESP32 Pinout Studio" and the domain stays esp32pin.com.** Only the copy widens to mention ESP8266.
- **No `Co-Authored-By` trailer on commits.**
- Run `npm test` before every commit. Run `npx tsc -b` before any commit that touches types.

## Verified Reference Data

Everything in this section was confirmed from a primary source during planning. Use it as given; do not re-derive it.

**ESP-12E/ESP-12F pad numbering** (from the official NodeMCU DevKit v1.0 schematic, sheet `02_ESP12_CORE`, and matching KiCad's `RF_Module:ESP-12E` symbol exactly):

| pad | function | pad | function |
|---|---|---|---|
| 1 | RST | 12 | GPIO10 / SPI_CS / SD_D3 |
| 2 | ADC / TOUT | 13 | SPI_INT / SD_D1 |
| 3 | EN | 14 | SPI_CLK / SD_CLK |
| 4 | GPIO16 / WAKE | 15 | GND |
| 5 | GPIO14 / HSPICLK | 16 | GPIO15 / HSPICS / RTS0 / TXD2 |
| 6 | GPIO12 / HSPIQ | 17 | GPIO2 / TXD1 |
| 7 | GPIO13 / HSPID / CTS0 / RXD2 | 18 | GPIO0 / SPICS2 |
| 8 | VDD | 19 | GPIO4 |
| 9 | SPI_MOSI / SD_CMD | 20 | GPIO5 |
| 10 | SPI_MISO / SD_D0 | 21 | GPIO3 / RXD0 |
| 11 | GPIO9 / SD_D2 | 22 | GPIO1 / SPICS1 / TXD0 |

**The SDIO to GPIO mapping** (ESP8266EX datasheet, confirmed by the NodeMCU schematic's own `SD_D3 GPIO10` / `SD_D2 GPIO9` net labels):

`SD_CLK = GPIO6`, `SD_D0 = GPIO7`, `SD_D1 = GPIO8`, `SD_D2 = GPIO9`, `SD_D3 = GPIO10`, `SD_CMD = GPIO11`.

This is the critical detail: KiCad's ESP-12E symbol names pads 9, 10, 13, and 14 as `CS0`, `MISO`, `MOSI`, and `SCLK` with **no GPIO number in the name**, and names pad 2 just `ADC`. The generator finds GPIOs by regex on the symbol pin name, so without an explicit pad-to-GPIO override, GPIO6, 7, 8, 11 and the analog input would be silently missing from the output.

**Boot rules, verbatim from the official NodeMCU schematic sheet `02_ESP12_CORE`:**
> On every boot/reset/wakeup, GPIO15 MUST keep LOW, GPIO2 MUST keep HIGH. GPIO0 HIGH -> RUN MODE, LOW -> FLASH MODE. When you need to use the sleep mode, GPIO16 and RST should be connected, and GPIO16 will output LOW to reset the system at the time of wakeup.

**NodeMCU v1.0 headers** (official schematic sheet `05_IO_CONN`, connectors J1 and J2, each `THT_Male_P_1x15`). J1 is the left column and J2 the right column when the board is viewed from the top with the USB connector at the bottom.

| 6 | SD1 | GPIO8 | 6 | 3V3 | VDD3V3 |

| J2 (left) | silk | net | J3 (right) | silk | net |
|---|---|---|---|---|---|
| 1 | RST | RST | 1 | TX | GPIO1 |
| 2 | A0 | A0 | 2 | RX | GPIO3 |
| 3 | D0 | GPIO16 | 3 | D1 | GPIO5 (SCL) |
| 4 | D5 | GPIO14 (SCK) | 4 | D2 | GPIO4 (SDA) |

| 6 | D7 | GPIO13 (MOSI) | 6 | D4 | GPIO2 |
| 7 | D8 | GPIO15 | 7 | G | GND |
| 8 | 3V3 | +3V3 | 8 | 5V | VBUS |

**D-label map** (upstream `arduino-esp8266`, `variants/nodemcu/pins_arduino.h` and `variants/d1_mini/pins_arduino.h`, both identical):

`D0=16, D1=5, D2=4, D3=0, D4=2, D5=14, D6=12, D7=13, D8=15`. NodeMCU additionally defines `D9=3` (RX) and `D10=1` (TX). `LED_BUILTIN=2` on both; NodeMCU also has `LED_BUILTIN_AUX=16`.

**ESPHome board keys** (confirmed present in `esphome/components/esp8266/boards.py`): `nodemcuv2`, `d1_mini`, `esp12e`, `esp01_1m`.

**A0 range:** 0 to 1.0 V on the bare ESP-12F. The LOLIN D1 mini product page states "1 analog input(3.2V max input)". NodeMCU v1.0 fits a divider on sheet `07_ADC`; its usable range is 0 to 3.3 V.

**Two facts that must not be modelled as per-pin capabilities:**
1. **I2C is software-only on the ESP8266.** There is no I2C peripheral. Any two usable GPIOs work. Arduino's `Wire` defaults to `SDA=GPIO4`, `SCL=GPIO5`. Do not tag `i2c` on individual pins; state it as a family note and as board silk labels.
2. **PWM is software-driven.** `analogWrite` works on any GPIO except GPIO16. Tag `pwm` on every usable pin except GPIO16.

// Espressif ships one flat .kicad_sym holding every symbol, so a symbol is a
// slice of that file. Find the slice for one symbol name.
function espBody(n) {
  const s = SYM.indexOf(`(symbol "${n}"`)
  if (s < 0) throw new Error('no sym ' + n)
  const re = /\n\t\(symbol "/g; re.lastIndex = s + 1
  let m, e = SYM.length; if (m = re.exec(SYM)) e = m.index
  return SYM.slice(s, e)
}

// KiCad's stock library is one file per symbol. An alias symbol carries no pins
// of its own and points at its parent with (extends "..."), so follow that to
// whichever ancestor actually draws the pins (ESP-12F extends ESP-12E).
function stockBody(n, depth = 0) {
  if (depth > 8) throw new Error('extends loop at ' + n)
  const t = fs.readFileSync(`${STOCK_SYM_DIR}/${n}.kicad_sym`, 'utf8')
  const ext = t.match(/\(extends "([^"]+)"\)/)
  return ext ? stockBody(ext[1], depth + 1) : t
}

const symBody = mod => (mod.lib === 'kicad' ? stockBody(mod.sym) : espBody(mod.sym))

// pad number -> pin name, for one symbol body.

  const p = new RegExp(PIN_RE.source, 'g')
  const o = {}; let x
  while (x = p.exec(r)) o[x[5]] = x[4]
  return o
}

## Notes for the implementer

- **If a verified source contradicts this plan, the source wins.** Every pin table here was read off a primary document during planning, but transcription errors are possible. Fix the plan's data, not the source.
- **The generator refactor in Task 2 touches shared code paths.** After running it, `git diff src/data/chips/generated.ts` must show only additions. Any change to an existing ESP32 module means the refactor broke something.
- **Do not add `i2c` capabilities to ESP8266 pins.** It is tempting because GPIO4/5 are the Wire defaults, but there is no I2C peripheral on this chip and claiming one would be exactly the kind of wrong-pin advice this site exists to prevent.
